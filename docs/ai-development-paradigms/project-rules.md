# 项目规则

本文档将 `multica-ai/andrej-karpathy-skills` 中的四个 Karpathy guidelines 落地到本项目。

## 规则 1：编码前先思考

核心思想：在写代码前先完成问题理解、方案拆解和风险识别。

在本项目中，任何实现任务开始前，都应先明确：

- 要解决的具体用户问题是什么。
- 输入来自哪里，例如 HarmonyOS 设备路径、本地数据库文件、分析条件或 MCP 客户端参数。
- 输出应该是什么结构，例如表结构、查询结果、聚合统计或错误信息。
- 哪些部分属于设备通信，哪些部分属于数据库访问，哪些部分属于 MCP 工具定义。
- 是否存在安全风险，例如直接拼接 SQL、暴露任意文件读取能力、误删设备文件。

执行要求：

- 不在需求模糊时直接写实现代码。
- 先列出最小可交付范围，再决定是否需要扩展。
- 对 `hdc`、SQLite、FastMCP 三类边界分别考虑失败场景。
- 对用户输入的查询条件优先设计结构化参数，不默认接受任意 SQL。

检查清单：

- [ ] 是否明确了本次任务的目标和非目标？
- [ ] 是否明确了输入、输出和错误格式？
- [ ] 是否识别了设备、文件、数据库、SQL 注入相关风险？
- [ ] 是否确认了最小实现路径？

## 规则 2：简单优先

核心思想：优先选择能清晰解决问题的简单方案，避免过早抽象和复杂框架。

本项目首选技术路线是：

- Python
- FastMCP
- Python 标准库 `sqlite3`
- HarmonyOS `hdc`

除非有明确需求，否则不要引入额外数据库 ORM、复杂任务队列、Web 框架或自定义查询语言。

执行要求：

- 先实现小而清晰的函数，再考虑抽象。
- 默认使用 `sqlite3` 的参数化查询能力。
- 默认通过 `subprocess` 封装 `hdc`，不要一开始构建复杂设备管理层。
- MCP 工具数量保持克制，围绕实际用例逐步增加。
- 配置文件、缓存目录、日志能力都应按需要添加，不提前堆叠。

检查清单：

- [ ] 是否可以用标准库解决？
- [ ] 是否引入了尚未被需求证明的依赖？
- [ ] 是否存在过早抽象的类或框架层？
- [ ] 是否能用更少的模块表达相同能力？

## 规则 3：外科手术式修改

核心思想：修改应精准、局部、可解释，避免顺手重写无关内容。

后续维护本项目时，每次变更都应尽量只触及与目标直接相关的文件。

推荐模块边界：

- MCP 工具定义：负责参数声明、工具注册、返回结构。
- HarmonyOS 设备通信：负责 `hdc` 检测、设备列表、文件拉取。
- SQLite 数据访问：负责连接、表结构读取、条件查询。
- 分析逻辑：负责对查询结果做统计、过滤、摘要。
- 测试：分别覆盖设备命令封装、查询构建和分析逻辑。

执行要求：

- 修复一个问题时，不重排无关文件格式。
- 添加一个能力时，不顺手重构未触及的模块。
- 修改公共接口时，同步更新相关测试和文档。
- 遇到脏工作区时，不覆盖用户已有改动。

检查清单：

- [ ] 本次修改是否只服务于当前目标？
- [ ] 是否避免了无关格式化或大面积重写？
- [ ] 是否清楚说明了修改范围？
- [ ] 是否保留了用户已有改动？

## 规则 4：目标驱动执行

核心思想：始终围绕最终目标推进，避免陷入局部优化或开放式探索。

本项目的长期目标是提供一个可被 MCP 客户端调用的工具，用于从 HarmonyOS 设备拉取数据库，并按照条件分析数据。

每次任务都应能映射到这个目标中的某一环：

- 设备连接与数据库拉取。
- 本地数据库识别与读取。
- 条件化查询与分析。
- MCP 工具暴露与返回结构。
- 错误处理、测试和使用文档。

执行要求：

- 开始任务前说明本次交付物是什么。
- 执行过程中优先完成可验证结果。
- 如果发现范围扩大，先收敛到当前最小目标。
- 完成后说明验证方式和剩余风险。

检查清单：

- [ ] 本次工作是否能直接支持 MCP 数据库分析目标？
- [ ] 是否有明确可验证的交付物？
- [ ] 是否避免了与目标无关的探索？
- [ ] 是否说明了完成状态、验证结果和后续风险？
