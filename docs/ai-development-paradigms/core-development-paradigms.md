# 核心开发范式 (Core Development Paradigms)

<rule>

## 核心架构：低耦合流水线与爆炸半径控制

在本项目中，所有业务逻辑的实现与修改，必须严格遵循【流水线拆分、步骤原子化、副作用隔离】的架构思想。严禁编写“一锅端”的巨型函数。

### 1. 主流程仅作调度 (Top-level Dispatcher Only)

- **行数与职责：** 业务入口主函数严禁超过 30 行，只能作为“数据传送带”按顺序链式调用子函数。
- **条件判断限制：**
  - [允许]：主函数内只能包含“卫语句（异常拦截）”或“顶层路由分发（决定走哪条支线）”。
  - [严禁]：绝对不允许在主流程直接编写“深层业务细节”（如拼装特定格式、计算数值、直接调用底层 API），这些必须下推到子函数。

### 2. 子函数的“契约化”与拆解 (Contract-Driven Atomic Functions)

- **单一职责：** 主流程拆分出的每一个子函数，只能执行单一的逻辑切片。
- **解耦替换：** 函数之间的依赖仅限于“数据结构契约”。只要保证输入/输出的类型不变，任何中间子函数都必须能够被轻易替换，而不影响上下游逻辑。严禁通过隐式全局变量传参。

### 3. 副作用隔离 (Side-Effect Isolation)

- 区分【数据处理函数】与【I/O 副作用函数】：
  - **核心业务逻辑（数据清洗/计算/组装）：** 必须是【纯函数】。严禁在函数内部直接修改（mutate）传入的原始数据对象，必须返回拷贝后的新对象。
  - **I/O 与副作用（网络请求/数据库操作/日志/鸿蒙系统能力调用）：** 允许非纯函数，但必须被【单独封装】在流水线的边缘节点，绝对不允许把副作用代码和数据计算逻辑揉杂在同一个函数里。

### 4. 影响面控制 (Impact Isolation)

- **精准狙击：** 面对需求变更或 Bug，必须精确定位到【唯一受影响的原子子函数】进行修改。
- **防御性契约：** 严禁为了修复单个子函数的内部逻辑，而随意修改它的入参/出参结构，从而强迫主管道及其他兄弟函数跟着“连带修改”。

</rule>
